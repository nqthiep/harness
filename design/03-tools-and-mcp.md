# 03 — Tools and MCP

**This file follows [`00-foundation.md`](00-foundation.md).** The vocabulary, `Effect`,
the two lattices, `Decision`/`Scope` are taken as-is from there, never redefined or
renamed. Every decision below cites a specific finding in [`research/`](../research/).

This file answers five questions: how a tool is declared, where its errors go, what runs
in parallel, how to retry a side effect without duplicating it, and how a stranger's tool
(MCP) gets classified.

---

## 1. `ToolSpec` — a tool author declares exactly one thing

### 1.1 Signature

```python
from collections.abc import Awaitable, Callable, Mapping
from enum import Enum
from typing import Any, Final, NewType

from harness._value import value
from harness.policy.base import Verdict

ToolName = NewType("ToolName", str)
ServerLabel = NewType("ServerLabel", str)
IdempotencyKey = NewType("IdempotencyKey", str)


class Effect(str, Enum):
    READ     = "read"
    WRITE    = "write"
    EXTERNAL = "external"
    DANGER   = "danger"


# No IdempotencyMode. The effect log is ALWAYS on for `write` and `danger` — see §4.5.
# The only thing left to declare is whether upstream accepts a key.


@value
class ToolSpec:
    __hash__ = None                      # holds a Mapping — not hashable

    name: ToolName
    description: str
    input_schema: Mapping[str, Any]
    fn: Callable[[Mapping[str, Any], "ToolCtx"], Awaitable[Any]]   # adapter GENERATED by @tool

    effect: Effect                       # <- THE ONLY THING a tool author has to think about

    # Runtime facts that can't be derived. NO `accepts_tainted` — see §1.1bis.
    upstream_accepts_key: bool = False   # only meaningful when effect in {WRITE, DANGER}
    server: ServerLabel | None = None    # None = a local tool; set = an MCP tool, see §5
    timeout_s: float = 30.0

    # Derived from `effect` — NOT a @tool parameter. Written out because 02 §4.1 reads them.
    @property
    def max_confidentiality(self) -> Confidentiality:
        """`write`/`external` are PUBLIC sinks; `read`/`danger` are unrestricted."""
    @property
    def emits(self) -> Label:
        """The label this tool's output carries. `external` -> UNTRUSTED, everything else TRUSTED."""
```

**Invariant T-1: no field of `ToolSpec` lets any of the five derived behaviors be
overridden.** No `parallel_safe`, no `handle_tool_error`, no `approval_mode`, no
`sequential`. To change behavior, change `effect`, and changing `effect` is a change a
reviewer can spot in a diff with a single word.

### 1.2 The derivation table — a usable version of [00-foundation §2]

```python
@value
class EffectProfile:
    parallel_safe: bool
    model_may_retry: bool        # the runtime may hand the error back to the model to retry
    runtime_auto_retry: bool     # the runtime may call it again on its own, SILENTLY, no asking the model
    taints_output: bool
    default_verdict: Verdict
    audit_level: str
    on_unexpected: "ToolOutcome"  # §2


#: A module constant, NOT configuration. Anyone who can edit this table can turn off
#: barriers and taint — 00-foundation R-3.
EFFECT_PROFILES: Final[Mapping[Effect, EffectProfile]] = {...}
```

| effect | parallel | model retry | runtime auto-retry | taints output | default verdict | audit | unexpected exception |
|---|---|---|---|---|---|---|---|
| `read` | yes | yes | yes (transport errors only, <=2) | no | `ALLOW` | `debug` | `FAILED` |
| `write` | no, barrier | yes (a key always exists) | no | no | `ASK` | `info` | `FAILED` |
| `external` | yes | yes | no | **yes** | `ALLOW` | `info` | `FAILED` |
| `danger` | no, barrier | no | no | no | `ASK` | **`audit`** | `FATAL` |

**A clarification, not a change.** [00-foundation §2] marks `external` as "retryable."
That's correct in the sense that *the model is allowed to retry* — a run doesn't die
because one fetch failed. It does **not** mean the runtime may silently retry it on its
own: the research states outright that *"an `external` tool that fails may have already
had an effect and must not be retried blindly"*
([§08](../research/08-tool-mcp-plugin.md) §8.2). So the `model_may_retry` and
`runtime_auto_retry` columns are split, and only `read` has the second column set to
`True`.

### 1.1bis Why `accepts_tainted` does NOT live on `@tool`

An early draft let a tool author set `accepts_tainted=True` and
`max_confidentiality=SECRET` right in the decorator. A reviewer pointed out those two
arguments have **exactly the shape** this very file accuses Microsoft of in §1.3, and
they disable **exactly the two** `DENY` branches the lattice provides
([review-security.md](review-security.md) S-16).

Scenario: a developer writes `run_shell` (`effect=danger`); during testing, an injection
from a web page makes every call get refused by `check_flow`; the fix appears right in
the signature — add `accepts_tainted=True`. A **one-line** diff, inside one tool's file,
touching no operator configuration, and a reviewer sees only a keyword argument sitting
between `effect=` and `name=`. That disables the integrity branch for exactly the
repo's most dangerous tool.

Invariant **T-1** lists what `ToolSpec` doesn't have — `parallel_safe`,
`handle_tool_error`, `approval_mode`, `sequential` — and missed two that are more
dangerous than all four of those combined.

> **Rule.** `accepts_tainted` and the confidentiality ceiling come **only** from
> operator configuration, keyed by tool name. The mechanism already exists for MCP tools
> in §5.2 (`policy.accepts_tainted: frozenset[ToolName]`) — a local tool uses **the
> same** mechanism, through `RunConfig`. There's no reason a local tool should be
> treated more leniently than a third-party one.

They are resolved at **bind** time (when the tool set attaches to an `Agent`), not at
**definition** time. The sentence "only the operator/local author may set this" in the
early draft is exactly where the hole was: that slash lumps together two principals with
two entirely different review processes.

### 1.3 The decorator — a missing `effect` is an import-time error

```python
def tool(
    *,
    effect: Effect | str,                    # keyword-only, NO default value
    name: str | None = None,
    upstream_accepts_key: bool = False,
    timeout_s: float = 30.0,
) -> Callable[[Callable[..., Awaitable[Any]]], ToolSpec]: ...
```

`effect` has no default, so forgetting it is a `TypeError` at tool-definition time — not
a silent default discovered after deployment. This is exactly where Microsoft slips:
their safety-critical decision sits in a decorator argument **with a default**, so
`@tool(name="mode_set", approval_mode="never_require")` looks like every other tool
under review ([§09](../research/09-memory-context-multiagent-hitl.md) §14.2). Here, a
switch that changes the safety mode cannot exist: it's `danger` by construction, and
[00-foundation §R-3] forbids any model-called tool from writing a `Decision`, loosening a
policy, or editing the `Ledger`.

### 1.4 One axis unifying three separate ideas

The research found three pieces of the same concept, in three projects, none aware of
the others:

| separate piece | what it covers | what it misses | how `Effect` unifies it |
|---|---|---|---|
| pydantic-ai's `sequential: bool` ([§08](../research/08-tool-mcp-plugin.md) §8.3) | a barrier for running in parallel — *"runs alone... other tools still run in parallel around it"* | says nothing about approval, retry, taint; and it's **the caller asserting it per tool** | `parallel_safe` is a derived column, §3 |
| pydantic-ai's `ToolKind = function \| output \| external` ([§08](../research/08-tool-mcp-plugin.md) §8.3) | `external` = a result generated by an outside service/person | it's a classification of **where a value came from**, not a safety classification | keeps the `external` name, adds taint semantics |
| MS's `disable_readonly_tool_approval` / `disable_write_tool_approval` ([§09](../research/09-memory-context-multiagent-hitl.md) §14.2) | read and write get separate gates — the right axis, the right place | only two tiers, and only used for approval | `default_verdict` is a derived column, four tiers |
| MCP's `readOnlyHint` / `destructiveHint` ([§08](../research/08-tool-mcp-plugin.md) §9) | a vocabulary describing effect for third-party tools | self-admits it's a *hint*, "clients should never make tool use decisions based on" them | only allowed to be a **default** for an already-trusted server, §5 |

All four are describing the same question — *what does this tool do to the world* — in
four different vocabularies. This harness asks that question **once**, and everything
else is a consequence.

## 2. Tool error taxonomy — learned from pydantic-ai, but derived from effect

### 2.1 The best design found, and why it still isn't enough

pydantic-ai is the only project in the research with a three-branch taxonomy
([§08](../research/08-tool-mcp-plugin.md) §8.2):

| raise | model sees it | a corrective prompt | spends retry budget | run continues |
|---|---|---|---|---|
| `ModelRetry` | yes | yes | **yes** | yes |
| `ToolFailed` | yes | no | **no** | yes |
| everything else | no | — | — | **no, the run ends** |

Distinguishing retry budget is the subtle part, and it's correct: a wrong argument
should burn correction quota (the model is guessing and needs to be reined in); a
definitive 404 should not (retry doesn't help, the model needs to *adapt*), and repeated
`ToolFailed` is capped at the run level by `UsageLimits`.

**The remaining shortcoming: the tool author has to pick the right branch.** And the
research has direct evidence that per-tool choice gets picked wrong: LangChain defaults
`handle_tool_error: ... = False`, meaning **a tool that raises kills the whole run**, and
recovery only happens if the tool's author remembers to opt in for that specific tool
([§08](../research/08-tool-mcp-plugin.md) §8.2). The research's own conclusion:

> *"neither default is right for every tool, which means the choice belongs to the
> tool's classification, not to a flag on each tool."*

### 2.2 This design: the author describes **what happened**, the runtime picks **the policy**

Two exceptions, and their names say *what happened*, not *what the runtime should do*.
This differs from `ModelRetry` — that name invites the tool author to make a policy
decision, which isn't the tool author's job.

```python
class ToolInputInvalid(HarnessError):
    """A call that's wrong and fixable: a missing field, a wrong type, an out-of-range value.

    Contract: raising this means the tool has NOT caused any side effect yet.
    """
    def __init__(self, *, what: str, got: object, fix: str, doc: str) -> None: ...


class ToolUnavailable(HarnessError):
    """The operation ran to completion and failed definitively: a 404, denied permission,
    a missing capability.

    Retrying doesn't help; the model needs to adapt.
    """


class ToolOutcome(Enum):
    RETRY  = "retry"   # the model sees it + a corrective prompt + SPENDS retry budget
    FAILED = "failed"  # the model sees it, no corrective prompt, does NOT spend retry budget
    FATAL  = "fatal"   # the run ends
```

The classification function — the entire error policy lives here, and it only reads
`effect`:

```python
def classify(exc: BaseException, spec: ToolSpec) -> ToolOutcome:
    """The error policy is DERIVED from the effect class, never a per-tool flag."""
```

| situation | `read` | `external` | `write` | `danger` |
|---|---|---|---|---|
| `ToolInputInvalid` | `RETRY` | `RETRY` | `RETRY` | `RETRY` |
| `ToolUnavailable` | `FAILED` | `FAILED` | `FAILED` | `FAILED` |
| a timeout (`timeout_s`) | auto-retries <=2 then `FAILED` | `FAILED` | `FAILED` if keyed, `FATAL` if not | `FATAL` |
| any other exception | `FAILED` | `FAILED` | `FAILED` if keyed, `FATAL` if not | `FATAL` |
| `CancelledError`, `KeyboardInterrupt` | **never classified — re-raised as-is**, §6 | | | |

Four things worth stating:

1. **`ToolInputInvalid` is always `RETRY` for every effect**, even `danger`, because its
   contract is that no side effect has happened yet. For `write` with a key, the
   runtime can actually **check** this contract: if the effect log already has a
   `committed` record for that call's key, the tool is lying and the outcome drops to
   `FATAL` (§4).
2. **An unrecognized exception on an unkeyed `write` is `FATAL`.** The reason is the only
   honest one available: the runtime *doesn't know* whether the side effect happened.
   Handing the error back to the model invites another call — exactly the path that
   produces a double effect, which
   [§03](../research/03-safety-reliability.md) §15 calls an industry-wide hole. This is
   also a design incentive: turning on idempotency *buys* a more durable run, and the
   cost of not turning it on is visible.
3. **`danger` is `FATAL` on any unexpected event.** For an irreversible operation, an
   unexpected error means the thing that must stop is the run, not just the next turn.
4. **Retry budget** is spent by `RETRY`, counted per `(run_id, tool)`, defaulting to 3.
   `FAILED` spends nothing — but every tool call is still logged to the `Ledger`
   ([00-foundation §6]), so infinite `FAILED` repetition is still capped at the run
   level by **both steps and money**. This is one notch stronger than pydantic-ai's
   `UsageLimits`, because [§03](../research/03-safety-reliability.md) §20 shows the
   industry has loop limits but almost no spend ceiling, and "a round with 200k input
   tokens costs a hundred times more than a short one."

**What this fixes:** there is no `handle_tool_error` field on `ToolSpec`, so there is no
per-tool choice to get wrong. Credit still stands for what LangChain does right: they
catch `KeyboardInterrupt` and **re-raise** it instead of swallowing it
([§08](../research/08-tool-mcp-plugin.md) §8.2); here that becomes a rule, see §6.

## 3. Parallelism and barriers — derived, not declared

### 3.1 The rule

One model turn produces `n` tool calls. The executor cuts that list into **segments**,
preserving the order the model emitted them in:

```python
def segments(
    calls: Sequence[ToolCall],
    specs: Mapping[ToolName, ToolSpec],
) -> list[list[ToolCall]]:
    """Segments run sequentially; within one segment, calls run in parallel.

    A call whose EFFECT_PROFILES[effect].parallel_safe == False sits ALONE in its
    own segment — that's the barrier.
    """
```

This is exactly pydantic-ai's primitive (its `'exhaustive'` mode: *"run every tool in
parallel, segmented only by `sequential=True` barriers"* —
[§08](../research/08-tool-mcp-plugin.md) §8.3), but the barrier's source differs: there
it's **a flag the caller asserts per tool**; here it's a consequence of `effect`.

### 3.2 Only one mode, and that's deliberate

pydantic-ai has three run-level modes (`'parallel'`, `'sequential'`, `'exhaustive'`).
This harness has **one**. The reason: a dial that can be turned to `'parallel'` is a dial
that can erase the barrier, i.e. a safety switch — [00-foundation §R-3] forbids that. The
one remaining dial is `max_concurrency: int` per run (borrowed from pydantic-ai's
constructor, [§02](../research/02-api-comparison.md) §6), and that's a resource limit,
not a safety limit: setting it to 1 makes things slower without losing any guarantee.

### 3.3 What this fixes

LangChain had to hand-write a dedicated guard for exactly one tool —
`middleware/todo.py:289`, *"Check for parallel `write_todos` tool calls and return
errors if detected"* ([§08](../research/08-tool-mcp-plugin.md) §8.3). The research
states the cost plainly: *"the guard exists only where someone was bitten, and the
twentieth tool has no guard at all."*

Here, `write_todos` is `effect="write"`, so it's a barrier from the line that declares
it, and so is the twentieth tool — nobody has to get bitten first.

### 3.4 Parallelism and taint

Several `external` calls in the same segment all taint context together. Label
composition is monotonic ([00-foundation §3.2]), so completion order doesn't change the
outcome. What makes this safe under concurrency is **where the label is stored**: the
thread's checkpointed state, not `threading.local()`. Microsoft puts middleware into
`threading.local()` and sets it across an `await`, and two concurrent tool calls read
each other's slot — silently, and fail-open
([§09](../research/09-memory-context-multiagent-hitl.md) §16bis). That's a defect *of
concurrency*, so it belongs to this section, not only to the taint section.

## 4. Idempotency at the tool-call level — where nobody else has it

### 4.1 What the research found

- **None of 16 packages have idempotency at the tool-call level** — exactly-once for a
  tool that already sent an email or already wrote to a database
  ([§07](../research/07-remaining-python.md) §CORRECTION).
- The closest thing is LangGraph's `CachePolicy`, and *caching is not exactly-once*
  ([§03](../research/03-safety-reliability.md) §15).
- **agno has it, but at the run-submission level**, a platform-layer concern: a
  partial-unique index in the DB, catching an `IntegrityError` and **re-reading to
  return the winner**, deliberately **never swallowing** a real error —
  *"Swallowing it as 'duplicate' would 202 a run that was never enqueued"*
  ([§07](../research/07-remaining-python.md) §CORRECTION).

The design below borrows agno's three technical details as-is and lowers the scope from
*run* to *tool call*.

### 4.2 Who generates the key

**The runtime, never the model, never the tool author.** A model generating the key
would grant itself the power to "call again as if it never happened" (a new key) or to
"block a legitimate call" (reusing an old key) — both are a safety switch in the
model's hands, [00-foundation §R-3].

```python
def call_key(
    run_id: RunId,
    call_id: CallId,
    tool: ToolName,
    args: Mapping[str, Any],
) -> IdempotencyKey:
    """blake2b(run_id | call_id | tool | canonical_json(args)) -> 128-bit hex.

    `call_id` is assigned by the runtime and lives in checkpointed state, so it's
    STABLE across a resume: replaying the same checkpoint regenerates exactly the
    same key. `args` is part of the key so a replay with edited arguments doesn't
    silently receive the old call's result.
    """
```

`canonical_json` = sorted keys, no whitespace, normalized numbers. Not `pickle` — that's
how LangGraph hashes its cache key, and it carries its own security implications when
input comes from an untrusted source ([§03](../research/03-safety-reliability.md) §15).

### 4.3 Where it's stored

One `effect_log` table, **in the same store as the checkpoint** — so it gets the same
durability guarantee, and so a resume can read it through the same connection:

```sql
CREATE TABLE effect_log (
    key         TEXT NOT NULL,
    run_id      TEXT NOT NULL,
    tool        TEXT NOT NULL,
    state       TEXT NOT NULL,          -- 'in_flight' | 'committed' | 'failed'
    result      BLOB,                   -- only when state='committed'
    error       TEXT,
    started_at  TEXT NOT NULL,
    ended_at    TEXT
);

-- A partial-unique index — learned from agno. A key may be "live" only once; a
-- 'failed' record (the tool never caused a side effect) frees the key for the next
-- legitimate attempt.
CREATE UNIQUE INDEX effect_log_live ON effect_log(key) WHERE state <> 'failed';
```

### 4.4 The three-phase protocol

```python
async def call_with_effect_log(
    spec: ToolSpec, args: Mapping[str, Any], ctx: "ToolCtx", log: "EffectLog",
) -> Any: ...
```

1. **Claim.** `INSERT (key, state='in_flight')`.
   - `IntegrityError` -> **never swallowed**; re-read the row and return the winner,
     exactly how agno handles the race
     ([§07](../research/07-remaining-python.md) §CORRECTION):
     - the winner is `committed` -> **`fn` is not called**, the stored result is
       returned, an audit event `duplicate_suppressed` is logged.
     - the winner is `in_flight` -> a previous execution is either still hanging or died
       mid-flight. The runtime *doesn't know* whether the side effect happened, so it
       **does not run it again**: it raises `AmbiguousEffect` -> `FATAL`, logs an
       `audit`-level event, and leaves the `in_flight` row for a human to resolve.
       Fail-closed.
2. **Execute.** Call `fn`. `ctx.idempotency_key` is always present for `write`/`danger`;
   when `upstream_accepts_key=True`, the tool is obligated to attach it upstream (an
   `Idempotency-Key` header, `client_reference_id`, etc.).
3. **Commit.** `UPDATE state='committed', result=...`, **before** the checkpoint records
   the tool result.
   - If `fn` raises `ToolInputInvalid` (contract: no side effect yet) -> `UPDATE
     state='failed'`, the key is freed.
   - **Every other exception leaves it `in_flight`.** This is the most important point
     in this section: not knowing means not freeing it.

**Invariant IDEM-1 (ordering)** — renamed from the original `I-1` (K-13,
`07-risks-and-open-issues.md` §1.5): the number `I-1` was already used by
`docs/02-architecture.md §2.3` for a COMPLETELY DIFFERENT invariant (reserving budget
before every model call — the same one `design/04 §3.3`'s "Invariant I-1" uses, written
before `docs/02` existed, same meaning). THIS invariant is about the order of writing the
effect log vs. the checkpoint for idempotency (T-6.1, not yet built in
`src/harness/`), unrelated to budget — two different concepts that happened to collide
on a number. `IDEM-1`: the effect log is written **before** the tool runs; the
checkpoint is written **after** the tool finishes. So every broken window leans toward
safety: a crash after the effect log commits but before the checkpoint -> a resume
regenerates the same key, finds `committed`, returns the stored result, doesn't run it
again. Reversing the order loses that property.

### 4.5 Being honest about what this achieves

| effect | the harness guarantees | what it needs from upstream |
|---|---|---|
| `read`, `external` | — (repeating produces no new effect, or the effect is out of scope) | — |
| `write`, `danger` by default | **at-most-once**: no harness retry causes the side effect a second time | nothing |
| `write`, `danger` + `upstream_accepts_key=True` | **exactly-once**, as far as upstream honors the key | upstream accepts an idempotency key |

**Why there's no "off" tier.** An early draft had `IdempotencyMode.NONE` as the default,
and a reviewer pointed out that's exactly the failure class this design criticizes
elsewhere: shortcoming #5 only gets fixed for whoever remembers to opt in, exactly like
LangChain's per-tool `handle_tool_error` and Microsoft's un-wired security module
([review-kiss.md](review-kiss.md) K-25). The effect log is now always on for
`write`/`danger`; the three-value enum shrank to one `bool`. This change made the design
**both simpler and more honest about its own promise**.

The harness alone can't promise exactly-once: if the process dies right while an HTTP
request is in flight, no local record can distinguish "it arrived" from "it didn't."
`KEYED` turns that into a stopped run and a visible `in_flight` row, instead of an email
sent twice. That's the whole promise, and it's still more than what the 16 packages
surveyed provide ([§07](../research/07-remaining-python.md) §CORRECTION).

## 4bis. `Sandbox` and `Workspace` — what gets enforced, and what does NOT

`Workspace` appears in every example from Tier 2 on and is required once the tool set
has `write`/`external`/`danger`. An early draft required it without specifying a single
line of what it does ([review-kiss.md](review-kiss.md) K-26) — i.e. promising isolation
without saying isolation of what. That's exactly Goose's mistake: four permission modes,
a removed sandbox seatbelt, and the tool still running with the user's own permissions
([§05](../research/05-ideal-harness.md) §31-8).

```python
class Sandbox(Protocol):
    """The enforcement boundary for local tools. MCP tools don't go through this — see §5."""
    async def open(self, run_id: RunId) -> SandboxHandle: ...

@value
class Workspace(Sandbox):
    root: Path                      # the one directory a tool may read/write
    egress: Egress = Egress.DENY    # DENY | Allowlist(hosts)
    max_bytes: int = 256 * 1024 * 1024
    max_procs: int = 0              # 0 = no child processes allowed
```

### Where it's enforced

| guarantee | enforced by | tier |
|---|---|---|
| a tool can't read/write outside `root` | resolve the path then check `is_relative_to(root)`; reject `.`/`..` segments; reject a symlink/reparse point **before opening it** | **Prevent** |
| a tool can't open a connection outside `egress` | an HTTP client injected into `ToolCtx`, bound to the allowlist; DNS resolved first, then the IP is pinned | **Prevent** for a tool using the injected client |
| a tool can't spawn a process | `max_procs=0` enforced at the process layer where available (`RLIMIT_NPROC`, a job object) | **Detect** where unavailable |
| a tool can't write past `max_bytes` | checked after every `write`, the run is aborted if exceeded | **Detect** |

The path rule learns exactly where Microsoft gets it right: rejecting `.`/`..` segments
**and** checking for a symlink/junction before opening, rather than just calling
`resolve()` once ([§09](../research/09-memory-context-multiagent-hitl.md) §14.2).

### What is NOT guaranteed — read this section carefully

This is the most important section, because Goose's mistake was exactly promising more
than it could enforce.

1. **`Workspace` is not an OS-level security boundary.** It's an in-process boundary. A
   deliberately malicious Python tool that calls `open()` or `socket()` directly instead
   of the injected client **cannot be blocked** by `Workspace`. It defends against a
   *carelessly written tool* and *a model under injection*, not against *a hostile tool
   author*.
2. **Defending against a hostile tool author needs a process boundary** — a container,
   gVisor, seccomp, or Firecracker. The harness defines `Sandbox` as a `Protocol`
   exactly so that can be plugged in; `Workspace` is the default implementation, not the
   only one.
3. **`egress` cannot block exfiltration through an allowed tool.** If the allowlist
   permits `docs.python.org`, a tool can smuggle data into a query string sent to that
   host. Preventing that leak is the job of the `confidentiality` axis in the lattice
   ([00 §3.2](00-foundation.md)), not of `egress`. Two different mechanisms — don't
   mistake one for covering the other.
4. **MCP tools don't go through `Workspace`** — they run in a different
   process/host. Their boundary is `ServerLabel` (v1) + the operator's policy, §5.

Stating these four things plainly matters more than adding a fifth mechanism: a
guarantee a user *thinks* they have is more dangerous than one they know they don't.

## 5. MCP — classifying a stranger's tool

### 5.1 A constraint from the protocol itself

`mcp_types` 2.1.1's `ToolAnnotations` says this about itself
([§08](../research/08-tool-mcp-plugin.md) §9):

> *"all properties in ToolAnnotations are **hints**. They are not guaranteed to provide a
> faithful description of tool behavior... Clients should never make tool use decisions
> based on ToolAnnotations received from untrusted servers."*

An annotation is **the unverified self-declaration of the very party being governed**.
The research's conclusion is a mandate for this section:

> *"A harness must classify third-party tools itself — from an operator-controlled
> policy keyed to the server's identity, with the MCP hints used at most as a default
> for servers already trusted, and never as the decision."*

### 5.2 Operator-held policy, keyed by server **label** (v1)

An early draft keyed this by a `ServerIdentity{label, fingerprint}` — `fingerprint`
defending against exactly one scenario: label A gets re-pointed to a different endpoint,
and an old grant wrongly follows the new endpoint. A reviewer pointed out the
`fingerprint` format was never nailed down (no obvious SPKI equivalent for MCP stdio —
see "Not Enough Evidence" at the end of this file) — a field whose format can't be
settled shouldn't enter a public type yet ([review-kiss.md](review-kiss.md) K-12). v1
keys on `ServerLabel` (a string) — that's the part **with** evidence, and the only
confused-deputy defense found in the entire research effort (Microsoft's
`server_label`). Stating plainly what v1 does **NOT** block: if a label gets re-pointed
to a different endpoint, an old grant still follows it — see `07-risks` for the
condition under which `ServerIdentity`/`fingerprint` gets added back (once a real
re-pointing incident is observed).

```python
@value
class McpServerPolicy:
    identity: ServerLabel
    trusted: bool = False                               # whether hints may be used as a default
    default_effect: Effect = Effect.DANGER              # used when untrusted, or hints are absent
    effects: Mapping[ToolName, Effect] = MappingProxyType({})     # operator override, per tool
    accepts_tainted: frozenset[ToolName] = frozenset()  # operator ONLY — never from a hint
    allow: frozenset[ToolName] | None = None            # None = every tool the server advertises


def classify_mcp_tool(tool: "McpTool", policy: McpServerPolicy) -> ToolSpec:
    """Builds a ToolSpec for a third-party tool. Priority order: policy > hint > default."""
```

### 5.3 Four rules

**M-1. A server not on the operator's trusted list -> annotations play no part in
classification.** Read only for logging, nothing more. `effect =
policy.effects.get(name, policy.default_effect)`, defaulting to `DANGER`. This matches
the exact polarity the MCP spec itself chose — a missing annotation means
*destructive*, *open-world*, *non-idempotent* — and the research flags it as worth
copying: *"the spec fails closed on every axis... that is the opposite of how most
optional metadata is designed"* ([§08](../research/08-tool-mcp-plugin.md) §9). The
ergonomic cost is real, and the escape hatch is `policy.effects`: the operator lowers
individual tools, by hand, once.

**M-2. A trusted server -> hints become the DEFAULT, mapped fail-closed.** An override
in `policy.effects` always wins over a hint.

```python
def _effect_from_hints(ann: "ToolAnnotations | None") -> Effect:
    """Fail-closed like Microsoft's `_map_mcp_annotations_to_labels`."""
    if ann is None:
        return Effect.DANGER
    if ann.read_only_hint is True:                       # ONLY True, not "anything but False"
        return Effect.READ if ann.open_world_hint is False else Effect.EXTERNAL
    if ann.destructive_hint is False:
        return Effect.WRITE
    return Effect.DANGER
```

The `is True` check is an expensive lesson from Microsoft, copied verbatim: *"real-world
servers (e.g. GitHub's MCP) declare `readOnlyHint=True` on read tools but leave the
field unset on write tools, so a strict `readOnlyHint=False` check would miss them"*
([§08](../research/08-tool-mcp-plugin.md) §9). Every value **other than `True`** — false
*or missing* — is a write sink.

One place this goes further than Microsoft: `read_only_hint=True` +
`open_world_hint` not `False` -> `external`, meaning **the output taints context**.
Microsoft exempts read-only tools from taint (*"they are safe to call even when the
agent context is tainted — it cannot exfiltrate"*,
[§09](../research/09-memory-context-multiagent-hitl.md) §16bis). That's correct along
the exfiltration direction but misses the other one: a read-only tool that reads from
the internet is a first-class prompt-injection source.

**M-3. `accepts_tainted` and the confidentiality ceiling NEVER come from a hint.** Only
`policy.accepts_tainted`, written by the operator. This is the fix for a gap Microsoft
still has, and the research names it directly: their mapping turns
`readOnlyHint=True` into `accepts_untrusted=True`, so *"the mapping is conservative
about a server that stays silent and trusting of a server that speaks"*
([§08](../research/08-tool-mcp-plugin.md) §9). A hostile server only has to declare
`readOnlyHint=true` to run inside already-tainted context. The research also points out
why that hole is absurd: *"It takes no server-trust parameter — only
`default_integrity` — even though the same codebase has a `server_label` trust boundary
in `_tool_approval.py`"*. Those two things sit in the same codebase and are never
connected. `classify_mcp_tool` receiving `McpServerPolicy` is exactly that connection.

**M-4. A grant is keyed by server label (v1).** [00-foundation §4.1]'s `Scope.server`
matches against `ServerLabel`. A `Decision` approving `search(query="x")` on server A
does not approve the same-named tool on server B. What v1 does NOT lock down (K-12, see
§5.2): after label A is re-pointed to a different endpoint, an old grant still follows
it to the wrong endpoint — that part needs `ServerIdentity` + `fingerprint`, deferred
until real re-pointing evidence shows up (`07-risks`).

### 5.4 Rug-pull: classification is fixed at bind time

`tools/list` can return different results between two calls. So a `ToolSpec` built from
MCP is **fixed into the run's checkpointed state**. If a re-list changes a tool's
`input_schema` or annotations while it's in use, it's treated as a **new tool**:
reclassified per M-1…M-3, and no old `Decision` carries over, because `Scope` is keyed
by `args`, not just by name ([00-foundation §4.1]).

## 6. Cancel — learned from autogen's discipline

### 6.1 The evidence

autogen-agentchat has a cancellation density of **26.9/kLOC**, three times the
second-place project (pydantic-ai at 9.1), and it isn't noise: 183 occurrences of
`cancellation_token` are **an explicit API parameter**, plus 84 occurrences of
`CancellationToken`. The research concludes this is the actor/.NET pattern —
*"cancellation is threaded by hand across every boundary, never relying on a runtime's
implicit mechanism... costlier in API surface, but the only way that makes cancellation
testable"* ([§07](../research/07-remaining-python.md) §New Finding).

### 6.2 The design

```python
# Canonical definition in 04-runtime-durability.md §6.1 — used only, here.
from harness import CancelToken
    async def wait(self) -> str: ...          # returns a reason, to race against work

    @property
    def cancelled(self) -> bool: ...
    @property
    def reason(self) -> str | None: ...


@value
class ToolCtx:
    """The second argument of every tool fn. Everything a tool needs that it isn't
    allowed to fetch for itself."""
    run_id: RunId
    call_id: CallId
    cancel: CancelToken
    label: "Label"                            # 00-foundation §3.2
    idempotency_key: IdempotencyKey | None    # ALWAYS set when effect in {WRITE, DANGER}
    deadline: datetime
```

**`ctx` is OPTIONAL in the function a person writes, required in the `fn` the runtime
calls.** Two different things, and an early draft conflated them
([review-kiss.md](review-kiss.md) K-16).

`@tool` reads the original function's type hints, generates `input_schema` from them,
and wraps it into the `(Mapping, ToolCtx) -> Awaitable` adapter. A tool author writes a
plain Python function:

```python
@tool(effect=Effect.READ)                     # sync, named parameters, no ctx
def word_count(text: str) -> int:
    return len(text.split())

@tool(effect=Effect.WRITE)                    # async, has ctx because it needs the key
async def send_email(to: str, body: str, *, ctx: ToolCtx) -> str:
    ctx.cancel.raise_if_cancelled()
    return await mailer.send(to, body, idempotency_key=ctx.idempotency_key)
```

The injection rule: the adapter passes `ctx` **only if** the original function declares a
keyword-only parameter named `ctx`. A sync function runs in a thread pool. Without
`ctx`, a tool has no access to the cancel token, the idempotency key, or the label — a
safe default, and the author of `word_count` doesn't have to learn three concepts to
count words.

For a tool that needs it, the token still crosses the boundary **by type, not by
convention** — exactly what autogen does, unlike every project relying on an implicit
`task.cancel()`.

### 6.3 Four rules

Naming them `CAN-1…4` (not `C-1…4`) is deliberate: `05 §A.1` has four SPEND invariants
also numbered `C-1…4` — the two namespaces collide by coincidence, unrelated to each
other ([review-kiss.md](review-kiss.md) K-13).

**CAN-1. `CancelledError` and `KeyboardInterrupt` never become a tool result.** They
skip `classify()` (§2) and are re-raised as-is. LangChain gets this right — they catch
`KeyboardInterrupt` and re-raise instead of swallowing it, and the research notes
*"a bare `except Exception` here would have made Ctrl-C unreliable"*
([§08](../research/08-tool-mcp-plugin.md) §8.2).

**CAN-2. A timeout is a cancel, not a second mechanism.** `spec.timeout_s` expiring ->
the runtime calls `token.cancel("timeout")`. One path, one place to test.

**CAN-3. Cancel does not roll back.** A `write` cancelled mid-flight leaves an
`in_flight` row in the effect log, and §4.4 handles the rest. Cancelling is *stop doing
more*, not *undo*, and pretending otherwise is exactly how a double effect gets
produced.

**CAN-4. A segment boundary is a clean cancel point.** Since `write`/`danger` are
barriers (§3), no tool call is in flight between two segments, so cancelling there
leaves an unambiguous state. The barrier hands back a second property, beyond its
concurrency correctness.

## Not Enough Evidence

- **The ergonomic cost of `default_effect = DANGER` for an untrusted MCP server.** The
  polarity matches the MCP spec, but there's no data on how many operators would bulk
  lower everything to `read` just to get past it — turning a safe default into a ritual.
  Needs measurement with real users, not something derivable from source.
- **Reconciliation for an `in_flight` row.** §4.4 stops the run and leaves the row for a
  human. Asking upstream *"was this command already written?"* needs a protocol no API
  in the research provides uniformly, so it's out of this file's scope.
- **The retry budget threshold of 3.** This number has no evidence in the research; it's
  a reasonable-feeling default, configurable, and needs evaluation to tune.
- **Rug-pull via `tools/list` (§5.4).** The research proves an annotation is an
  unverified self-declaration ([§08](../research/08-tool-mcp-plugin.md) §9); a
  declaration *changing* between two lists is a natural consequence but was **not
  directly observed** in any source read. Rule M-4/§5.4 is preventive, not a reaction
  to a measured incident.
- **The cost of writing the effect log on every `write` call.** One extra DB round-trip
  per side-effecting tool call. Not measurable from anyone else's source; needs this
  repo's own benchmark.
- **The `fingerprint` format for `ServerIdentity`.** TLS SPKI pinning fits the HTTP
  transport but has no obvious equivalent for MCP stdio (a child process). Not enough
  evidence to settle it — §5.2 now keys v1 on `ServerLabel` (a string) instead of
  waiting on `fingerprint`, and `ServerIdentity`/`fingerprint` won't be added back until
  a real label re-pointing incident is observed (K-12).
